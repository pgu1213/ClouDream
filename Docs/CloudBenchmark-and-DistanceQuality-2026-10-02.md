# 이동 벤치마크와 거리별 밀도·조명 품질

## 사용자 요구와 이번 범위

벤치마크를 먼저 구현·Play 검증한 뒤 세 번째 최적화인 거리별 밀도·조명 품질 분리를 추가했다. 실시간 유체 반응과 다른 최적화는 포함하지 않았다. 목표는 GTX 1660 / 1920×1080 / 60 FPS이며 이번 실측 장치는 RTX 4080이다. 목표 GPU의 성능으로 환산하지 않는다.

FluidNinja 자료에서 참고한 것은 화면 기여도가 낮은 먼 영역의 계산 빈도를 낮추고 계산 종류별 품질을 분리하는 원리다. 이 구현은 Unity HDRP CustomPass와 현재 볼륨 광선 적분기에 맞춰 새로 작성했다. 언리얼 코드나 수작업 복원본을 원본 Unity 구현으로 취급하지 않았다.

## 사용 방법

1. `LostSkiesCloudSea`에서 Play를 시작한다. Game 뷰 해상도를 원하는 값으로 정한다. 이번 비교는 FHD다.
2. **F8**에서 기존 품질 옵션과 `Distance density`, `Distance lighting`을 독립적으로 변경한다. 각각 시작 거리, 완전히 낮아지는 거리, 최대 표본 간격 배율을 조절할 수 있다.
3. **F9** 또는 F8의 `Open repeatable benchmark`로 전용 창을 연다.
4. `Run current settings`는 현재 설정을 측정한다. 거리 비교에서 `Density only / Lighting only / Both`를 선택한 뒤 `Compare selected mode`를 누르면 **OFF → 선택한 옵션 ON → 선택한 옵션 ON → OFF**로 측정한다. 다른 품질 설정은 유지하며 비교가 끝나면 원래 선택을 복원한다.
5. `Quick / Standard / Long`은 시점당 60 / 180 / 600 표본이다. Standard는 조건마다 540프레임이다. 전체 경로를 먼저 한 번 워밍업하고, 시작점에서 32프레임 안정화한 뒤 측정한다.
6. Escape로 취소한다. 부분 결과는 `cancelled`로 저장되며 완료된 결과와 구분한다.

에디터 결과는 프로젝트의 `Benchmarks/`, Player 결과는 `Application.persistentDataPath/CloudBenchmarks/`에 시각이 포함된 JSON과 CSV로 저장된다. 매번 파일을 덮어쓰지 않는다. 원시 결과는 `.gitignore`에 포함되며 이 문서의 검사 결과와 별개로 로컬에 남는다.

## 경로와 비교 조건

`CloudRoute-v1`은 현재 Concept V2의 대표 구름 중심 주위를 한 바퀴 도는 경로, 구름을 관통하는 경로, 운해를 내려다보며 이동·회전하는 경로로 구성된다. FOV는 68도다. Inspector의 `routeCenter`로 궤도/관통 중심을 정할 수 있고 실제 사용한 중심과 모든 프레임의 자세를 보고서에 남긴다. 운해 경로는 v1의 고정 좌표다.

프레임 번호에 따라 같은 자세를 적용한다. 따라서 비교 조건마다 같은 화면을 계산하지만, 실제 시간 기준 이동 속도는 FPS에 따라 달라진다. 게임 시간을 정지해 바람, 날씨와 시간 전환을 같은 상태로 유지한다. 성능 측정용 경로이며 실시간 이동 재생의 속도 비교는 아니다. 각 경로 사이의 시점 전환 비용은 측정에 포함된다.

벤치마크 동안 VSync와 FPS 제한을 해제하고 실행을 백그라운드에서도 계속한다. Game 카메라만 구름 패스를 실행하도록 제한하여 Scene 뷰 GPU 마커가 합산되지 않게 한다. 카메라 위치·회전·FOV, 입력 컴포넌트, 커서, 시간 배율, VSync, FPS 제한, 백그라운드 설정, 에디터 Profiler 설정은 완료·취소·컴포넌트 비활성화 때 복원한다. 해상도가 도중에 바뀌면 실패로 기록한다.

## 계측 데이터의 의미

| 항목 | 기준 |
|---|---|
| 평균 FPS | 표본 수 / 총 실제 경과 시간. FPS 숫자들의 산술평균이 아님 |
| 최저 FPS | 가장 긴 단일 프레임 시간의 역수 |
| 1% low FPS | 느린 상위 1% 프레임의 평균 시간의 역수 |
| p50 / p95 / p99, 최대 지연 | 실제 프레임 간격, nearest-rank 백분위수 |
| 16.67 / 33.33ms 초과 수 | 각각 60 / 30 FPS 예산을 넘긴 프레임 수 |
| 구름 GPU | `Cloud.Total`, `Cloud.Raymarch`, `Cloud.DepthCopy`, `Cloud.Composite`의 GPU ProfilerRecorder 원시 표본과 표본 수 |
| CPU / GPU 프레임 시간 | FrameTimingManager의 타임스탬프, CPU 전체/메인/렌더 스레드, Present 대기, GPU 시간 |
| CPU 사용률 | 현재 Unity 프로세스 비율과 Windows 전체 비율을 구분. 프로세스 100%는 모든 논리 코어 사용 |
| GPU 사용률 | NVML의 해당 어댑터 전체 GPU 실행 비율. 다른 앱을 포함하며 Unity 전용 비율이 아님 |
| GPU memory busy | 메모리 접근이 활성화된 시간 비율. VRAM 점유 비율과 다름 |
| GPU 상태 | NVML의 실제 그래픽 클럭 MHz, GPU 온도, 어댑터 전력 W, P-state. 기준선 속도 변동 진단용 |
| RAM / VRAM | Windows 프로세스 working set와 private committed bytes, Unity allocated/reserved/managed, NVML 어댑터 전체 점유 VRAM |
| 디버깅 | 프레임별 GC 할당/수집 횟수, draw calls/triangles, 구름 RT/시간 이력/공간 캐시 바이트, RT 재할당/형태 캐시 생성/이력 초기화 누적 횟수 |
| 재현 조건 | 장치/OS/Unity/그래픽 API/논리 코어/메모리 용량, 장면, 셰이더 의존성 해시, 패스·프로필 설정, 내부·화면 해상도, 경로와 정지된 게임 시각 |

하드웨어 사용률과 메모리는 1초마다 수집하고 실제 계측 간격으로 평균을 가중한다. 메모리 최대값은 **표본에서 관찰된 최대값**이다. 폴링 소요 시간도 저장한다. JSON의 `-1`과 UI의 `N/A`는 미지원/실패다. 동일 이름의 NVIDIA GPU가 여러 개이면 임의의 장치를 선택하지 않는다. NVIDIA 라이브러리가 없으면 GPU 사용률 대신 N/A를 제공하고 나머지 측정을 계속한다. 현재 렌더러의 지원 대상은 Windows D3D12다.

GPU 마커와 FrameTiming은 지연된 독립 스트림이다. 이를 자세 CSV 행과 같은 프레임인 것처럼 연결하거나 각 마커의 백분위수를 합산하지 않는다. GPU 표본 수가 부족하면 그 수를 그대로 표시한다. FrameTiming GPU 평균이 구름 GPU 평균보다 작은지 검사하며, 이 검사 통과만으로 전체 GPU 계측의 정확성을 보증하지는 않는다. Editor·Profiler·벤치마크 자체 비용이 포함된다. 배포 성능 판정은 같은 조건의 Player와 목표 GPU에서 다시 측정해야 한다.

자동 비교는 같은 OFF끼리, 같은 ON끼리 구름 GPU 평균이 10% 이상 변하면 `INCONCLUSIVE`로 표시해 개선율 확정을 보류한다. 이는 2회 반복의 변동 검사이며 통계적 유의성 검정은 아니다. 비교 요약과 네 원시 결과의 경로도 별도 TXT로 남긴다.

Windows CPU/메모리 정의는 [GetSystemTimes](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getsystemtimes), [GetProcessMemoryInfo](https://learn.microsoft.com/en-us/windows/win32/api/psapi/nf-psapi-getprocessmemoryinfo), GPU 사용률 정의는 [NVIDIA NVML](https://docs.nvidia.com/deploy/archive/R550/nvml-api/group__nvmlDeviceQueries.html)을 따른다.

## 거리별 품질 구현

현재 검증한 Concept V2만 `CloudFormationProfile.SupportsDistanceQuality` 계약으로 지원을 선언한다. 다른 형태나 추출값 경로는 기존 품질로 처리한다. 두 옵션의 기본 상태는 OFF다. 기본 전환 거리는 **3,000–12,000m**, 밀도·조명 최대 간격 배율은 각각 **1.5배**다. Inspector에서 비정상 값이 들어와도 GPU 전송 시 유한값, 최소 전환 폭, 배율 상한을 보장한다.

- **밀도:** 빈 공간 탐색, 표면 이분 탐색, 밀도장 함수와 표면 법선을 유지한다. 실제 구름 내부의 적분 간격만 거리 smoothstep에 따라 늘린다. 밀도 배율은 1–2다. 실제 step 길이를 Beer–Lambert 투과율 적분과 깊이 모멘트에 사용한다.
- **조명:** 그림자 광선의 7개 표본, 하늘 차폐 3개 표본과 도달 범위를 유지한다. 주 광선의 입사광 보간 간격을 기본 60m에서 점차 넓힌다. 조명 배율은 1–3이다. 한 번 만든 보간 구간 끝은 고정하고 다음 구간부터 새 간격을 적용한다. 구름의 틈/새 표면에서는 이전 조명을 재사용하지 않는다.
- 새 RT나 노이즈 에셋은 만들지 않는다. 모든 활성 상태·거리·배율이 시간 재투영의 상태 키에 포함되어 설정 변경 직후 전체 갱신한다.
- 밀도와 조명의 활성 조합은 별도 셰이더 키워드로 분리한다. OFF 경로에 사용하지 않는 품질 계산과 조명 상태를 남기지 않는다. 각 조합은 최초 사용 시 셰이더 컴파일 시간이 들 수 있으며 벤치마크 워밍업에서 제외한다.

밀도 옵션은 먼 얇은 구름과 투과율에, 조명 옵션은 원경 명암에 차이를 만들 수 있다. 특히 원경 운해를 위에서 내려다보는 장면에서 차이가 상대적으로 크다. 2배 조명 간격에서 이 변화가 커 기본값을 1.5배로 낮췄다. 최대 배율은 화질 우선 기본값이 아니다.

## 검증

벤치마크를 세 번째 기능보다 먼저 실행해 180개 프레임/180개 GPU 표본 저장, 10/30ms 입력의 평균 FPS=50 및 최저 FPS=33.33 계산, 취소 시 실행 상태 복원을 확인했다. 초기 Unity Mono의 `Process.WorkingSet64`가 0을 반환하는 문제를 발견해 Windows 네이티브 메모리 계측으로 수정하고 실제 바이트 반환을 확인했다.

최종 Play 검사에서 F9 모달 입력 보존, 자동 비교 취소 후 원래 거리 옵션 복원, 컴포넌트 비활성화 복원을 통과했다. 실행 중 Game 뷰 해상도를 바꾸면 `failed`로 기록하고 시간 배율·Profiler·백그라운드 설정을 복원하는 것도 확인했다. 측정 실패를 정상 완료로 처리하지 않는다.

거리 GPU 검사는 12개 시나리오 × 7개 설정과 미지원 형태 복귀, 총 **85개 비교**, **8개 시간 이력 초기화 검사**를 수행했다. OFF는 수정 전 고정 셰이더와 RGB/투과율/깊이 오차 0이었다. 조명만 켜면 투과율·깊이 오차는 0이었다. 전체를 근거리로 둔 검사와 배율 1에서는 투과율 오차 0, RGB 최대 오차 0.000488(half 정밀도 수준), 평균 최대 약 1.66e-8이었다.

기본값 둘 다 ON의 시나리오별 평균 RGB 최대채널 오차는 약 0.00042–0.02010, 평균 투과율 오차는 최대 약 0.0000359였다. 국소 오차는 이 평균보다 클 수 있다. 아래에서 태양을 보는 극단 조명에서는 HDR RGB 최대 오차가 6.375, 일부 경계의 투과율 최대 오차는 약 0.701이었다. 수치는 선형 HDR 구름 출력이며 최종 톤매핑 화면의 백분율이 아니다. 극단값 검사는 유한값 안정성 검증이며 화질 동일성 보증이 아니다.

상층 분포 65,536개 표본, 반복/원점 이동 오차 0, 빈 셀/경계, 날씨 중단 및 즉시 전환 검사를 통과했다. 기존 GPU 반복 4회 검사도 오차 0이며 운해 투과율 상한은 약 0.007996이었다.

독립 비교용 수정 전 셰이더 SHA-256: `EC63A3437576ACAC5616FA5D77558C1461377C80F71278E2A90668C1B925ECA2`. 로컬 증거는 `Benchmarks/CloudDistanceBaseline.compute.txt`, `Benchmarks/DistanceQuality-Validation.json`이다.

독립 비교용 임시 Unity 셰이더 에셋은 검사 후 제거했다. 이후 검증기를 실행하면 현재 셰이더의 OFF 경로와 비교하며, 보고서의 `frozenBaseline`이 이를 구분한다.

## 성능 실측

RTX 4080 / Unity 6000.6.2f1 Editor / D3D12 / 화면 1920×1080 / 구름 75%를 사용했다. 내부 RT는 정렬을 포함해 **1440×816**이다. 낮 12시, 바람 0, 기본 형태 캐시·영역 거부·압축 RT·깊이 업샘플링 ON, 시간 재투영·공간 조명 캐시·팔레트 빠른 경로·빈 구간 생략·그림자 조기 종료 OFF다. 밀도/조명 전환은 각각 3–12km, 1.5배이며 이번 ON은 둘 다 켠 조건이다.

각 실행은 워밍업을 제외하고 프레임 **540개**, 구름 GPU 표본 **540개**, FrameTiming **540개**를 기록했다. 네 실행의 모든 자세, 정지 게임 시각, 셰이더 해시와 해상도가 동일함을 확인했다.

GPU 평균 클럭은 실행별 약 2736–2743MHz였다. 활성 구름 RT는 모두 **18,800,640바이트(17.93MiB)**, RT 할당 누적값은 측정 내내 1로 유지됐다. 새 기능 때문에 RT를 추가하거나 다시 할당하지 않았다. 프로세스/어댑터 전체 메모리의 변동을 이 기능의 메모리 증감으로 해석하지 않는다. Editor GC 수집은 실행별 1/0/1/1회였으며 해당 프레임을 최저 FPS에서 제외하지 않았다.
