# FluidNinja 원리를 적용한 구름 최적화 결과

**2026년 10월 2일 측정 정정:** `CloudSceneFramePerformance`의 side·inside 경로가 옵션마다 달라지는 오류를 후속 작업에서 수정했다. 아래 **실제 Game 카메라 측정**의 해당 두 행은 같은 시점의 A/B가 아니며, 그 증가율을 성능 회귀의 근거로 사용할 수 없다. home은 고정 시점이다. 별도 도구의 독립 dispatch·높이장 수치와 출력 정확성 검사는 이 오류와 구분한다. 구간 제한과 그림자 종료의 기본 OFF는 유지한다. 정정 경위는 [재구성 보고서](D:/Dev/ClouDream/Docs/CloudOptimization-Reconstruction-2026-10-02.md)에 기록한다.

후속 승인으로 진행한 [공간 조명 캐시 구현·검증](D:/Dev/ClouDream/Docs/CloudOptimization-SpatialLighting-2026-10-02.md)은 별도 보고서에 기록했다. F8에 실험 옵션을 추가했으며 기본 OFF다.

2026년 10월 1~2일, 사용자가 승인한 빈 구간 제한·그림자 조기 종료를 구현하고 운해 높이장 캐시를 평가했다. **두 새 옵션 모두 기본 OFF로 두고 F8에서 시점별로 선택하게 했다.** 독립 dispatch에서는 빈 구간 제한이 빨랐지만 실제 Game 카메라의 일부 비교는 위 측정 오류로 판단에서 제외한다. 높이장 캐시는 오차에 비해 개선이 작아 장면에 적용하지 않았다. 목표는 GTX 1660, FHD, 60 FPS지만 현재 검증 장비는 RTX 4080이며 목표 달성을 확인한 결과가 아니다.

## 사용자 요구와 참고 자료의 구분

기존 운해·상층 형태를 유지하면서 구름 렌더 비용을 줄이고, 차이가 있는 옵션을 Play에서 조작하도록 하는 것이 승인 범위다. 실시간 후류·유체 반응은 사용자의 이전 결정대로 후속 작업이다. Unreal의 Blueprint, Niagara, 머티리얼을 그대로 이식하지 않았다.

[FluidNinja 자료 검토](D:/Dev/ClouDream/Docs/FluidNinja-Optimization-Review-2026-10-01.md)에서 확인한 RayBox·높이 범위·광학 감쇠에 따른 종료 원리를 채택했다. 이번 Unity C#·HLSL은 현재 다층 절차식 구름에 맞춰 새로 설계했다. 자료의 수작업 복원본을 원본 소스로 표현하거나, 자료 내부 제안을 사용자 지시로 취급하지 않았다.

## 적용한 변경

| 항목 | 구현과 판단 | 장면 기본값 |
|---|---|---|
| 빈 구간 제한 | 운해의 높이 범위, 상층 타원체의 보수적 AABB, 띠구름의 지원 범위를 합쳐 빈 구간의 밀도 평가를 생략 | OFF, F8에서 시점별 비교 |
| 그림자 종료 | 팔레트 조명의 visibility가 포화되고 남은 rim 입사광이 0.0001 이하가 되는 광학 깊이에서 종료. 물리 조명·혼합 조명은 기존 조회 유지 | OFF, F8에서 비교 |
| 운해 높이장 | 512²의 정규화 높이·봉우리 마스크를 16/32/64m 격자로 시험. 외부는 절차식, 가장자리는 2 texel 보간 | 실험용 API·검사만 유지, 설정창에 미노출 |
| 셰이더 분기 | 구간 제한과 실험 높이장을 compute keyword로 분리하여 OFF에서는 관련 연산 제거 | 해당 옵션에 연동 |

빈 구간 제한은 근사 거리장을 큰 이동 거리로 사용하지 않는다. 기존 스텝 위치·진입 이분 탐색·1024회 상한을 유지하고 비싼 밀도 평가만 생략한다. 한 구름을 벗어나도 뒤쪽 셀을 계속 검사한다. 음수 셀, 축과 평행한 광선, 원점 이동을 포함해 검증했다.

높이 캐시는 `CloudFormationProfile.TryGetOceanHeightParameters`를 통해 형태 계약을 받는다. 카메라 창·지역 흐름·지형 파라미터 변경 시 갱신하고, 높이 진폭·날씨 값은 조회 시 복원한다. `CloudEnvironmentSource` 공급 계약을 유지했다. 기본 경로에서는 높이장 RT를 생성하지 않는다.

## 레이마칭 GPU 결과

Unity 6000.6.2f1, HDRP 17.7, Windows D3D12, RTX 4080, Editor Play에서 측정했다. FHD의 75%인 1440×816 구름 RT, 정오, 바람 오프셋 0, 1차 최적화 ON으로 입력을 고정했다. 케이스마다 워밍업 8개와 유효 표본 24개다. 장면 구름 패스를 수집 중 잠시 중단하고 완료 후 복원했다.

아래는 **독립 Raymarch dispatch의 GPU 타임스탬프 p50 / p95(ms)**다. 깊이 복사·합성·HDRP·캐시 생성 및 전체 프레임 시간은 포함하지 않는다.

| 시점 | 이번 변경의 두 옵션 OFF | 빈 구간 제한만 ON | 그림자 종료만 ON | 둘 다 ON | 구간 제한의 p50 감소 |
|---|---:|---:|---:|---:|---:|
| home | 102.54 / 112.18 | 80.33 / 83.33 | 99.28 / 105.06 | 80.44 / 83.82 | 21.7% |
| side | 82.10 / 92.28 | 55.03 / 55.68 | 88.05 / 96.85 | 64.98 / 67.11 | 33.0% |
| inside candidate | 14.62 / 15.66 | 11.83 / 12.48 | 13.52 / 14.18 | 11.17 / 12.28 | 19.1% |

그림자 종료를 추가하면 내부 시점은 구간 제한만 켠 경우보다 약 5.6% 빨랐지만, 측면은 약 18.1% 느렸다. 분기·GPU 실행 효율의 구체적 원인은 별도 분석하지 않았다. 모든 시점에서 유리하다고 가정하지 않고 기본 OFF로 정했다.

수정본 OFF와 비교하는 데서 그치지 않고 작업 시작 커밋 `fcc36bf2c2fceeb0c1004771e47d7de938bade95`의 셰이더·형태 함수를 임시 복사해 같은 정오·바람·시점으로 측정했다. 그 p50은 home 93.80ms, side 86.34ms, inside 14.10ms였고, 구간 제한 ON은 각각 약 14.4%, 36.3%, 16.0% 낮았다. 임시 에셋은 Unity MCP로 삭제했다. 이 별도 순차 실행은 Editor 스케줄링 변동이 포함되므로 정밀한 제품 성능 보증으로 사용하지 않는다.

1차 보고서의 조명·바람 입력과 이번 고정 입력은 다르다. 두 보고서의 절대 시간을 직접 이어 붙여 누적 개선율을 계산하지 않는다.

## 실제 Game 카메라 측정과 기본값 결정

FHD Game 뷰에서 HDRP가 실행하는 실제 구름 패스를 추가로 수집했다. 검사 중에만 Volume을 Game 카메라로 한정해 Scene 뷰의 마커가 섞이지 않게 했다. 각 조건의 워밍업은 20개, 유효 표본은 48개다. 정오·바람 0·75% 해상도·1차 최적화 ON·그림자 종료 OFF를 유지했다.

| 시점 | 구간 OFF Raymarch p50 / p95 ms | 구간 ON Raymarch p50 / p95 ms | p50 변화 |
|---|---:|---:|---:|
| home | 63.28 / 71.78 | 52.68 / 60.49 | 16.8% 감소 |
| side | 49.32 / 56.16 | 54.38 / 63.89 | 10.3% 증가 |
| inside candidate | 10.90 / 12.27 | 14.14 / 16.73 | 29.7% 증가 |

위 표는 최초 기록이며 **side·inside의 증가율은 시점 차이 때문에 무효**다. 깊이 복사의 p50은 약 0.0082ms, 합성은 약 0.0348~0.0358ms였다. 이 경로에서는 두 작업보다 Raymarch가 큰 비용을 차지한다. 독립 dispatch와 실제 패스는 깊이 입력 및 GPU 실행 조건이 다르다. **독립 테스트의 19~33% 감소를 실제 게임의 일관된 개선율로 주장하지 않는다.** 구간 제한은 실제 장면의 유효 비교를 충분히 확보할 때까지 기본 OFF를 유지한다.

`FrameTimingManager`의 원시 GPU p50은 이 검사에서 약 0.76~0.81ms로 같은 장면의 Raymarch보다 짧았다. 6조건 모두 GPU 시간의 기본 일관성 검사를 통과하지 못해 **전체 장면 GPU p50·p95는 확정하지 못했다.** CPU p50은 home 65.57→54.83ms, side 51.85→57.48ms, inside 13.14→17.14ms였지만 Editor 스케줄링이 포함되므로 Player FPS로 해석하지 않는다. [Unity 공식 문서](https://docs.unity3d.com/6000.0/Documentation/Manual/frame-timing-manager.html)도 반환 지연이 정확도를 보장하지 않으며 Profiler 검사를 대체하지 않는다고 설명한다. 이 환경의 문제 원인을 문서만으로 단정하지 않았다.

[실제 패스 마커와 프레임 API 원시 기록](D:/Dev/ClouDream/Screenshots/RayOptimization-SceneFrames.json)을 함께 보관했다. 재현 메뉴는 FHD Game 뷰의 Play에서 **Measure FHD Scene Frames**다. 검사가 끝나면 카메라 지정·입력·프로파일러·렌더 설정을 복원한다.

## 높이장 캐시를 기본으로 채택하지 않은 이유

같은 세 시점에서 구간 제한·그림자 종료를 고정하고 캐시 준비부터 Raymarch까지 측정했다. 강제 갱신은 매 dispatch마다 캐시를 무효화하여 생성 비용을 포함한다. 수치는 p50 / p95(ms)다.

| 시점 | 절차식 | 16m float | 32m float | 32m 매번 재생성 |
|---|---:|---:|---:|---:|
| home | 85.33 / 89.18 | 100.90 / 109.07 | 84.40 / 89.72 | 86.23 / 92.20 |
| side | 68.60 / 77.51 | 70.37 / 73.59 | 67.20 / 70.92 | 70.50 / 76.00 |
| inside candidate | 11.49 / 12.62 | 11.31 / 12.34 | 11.07 / 12.20 | 11.30 / 12.24 |

32m 안정 상태의 p50 개선은 약 1.1~3.6%다. 재생성 비용·측정 변동까지 고려하면 확실한 큰 이득으로 보기 어렵다. 16m는 캐시가 덮는 월드 범위도 줄어들며 home에서 오히려 느렸다. 형식별 32,768개 표본과 320×184 영상 비교 결과는 다음과 같다.

| 격자·형식 | 메모리 | 최대 / 평균 높이 오차 m | 창 이동 전후 최대 높이 변화 m | 최대 RGB 차이 |
|---|---:|---:|---:|---:|
| 16m RGFloat | 2 MiB | 2.733 / 0.234 | 2.349 | 0.1172 |
| 32m RGFloat | 2 MiB | 3.306 / 0.264 | 3.130 | 0.1211 |
| 64m RGFloat | 2 MiB | 7.791 / 0.355 | 6.496 | 0.1152 |
| 32m RGHalf | 1 MiB | 3.270 / 0.343 | 2.795 | 0.1191 |

격자별 검사 범위는 texel 크기×600으로 서로 다르므로 이 평균만으로 정밀도 우열을 단정하지 않는다. 32m float의 최대 밀도 차이는 약 0.092, 가중 깊이 차이는 20m였다. 캐시 재사용·원점·파라미터 갱신·환경 복구 계약은 통과했지만, 이는 시각 품질 통과를 뜻하지 않는다. 창 이동 시 형태 변화 가능성도 남아 있어 품질 옵션으로 승격하지 않았다.

## 검증과 Play 사용법

- 빈 구간·그림자 단독 및 조합: 12조건×3변형, 총 36개 비교 통과. 빈 구간 제한은 RGB·투과율·가중 깊이 차이 0. 그림자 종료의 최대 RGB 차이는 0.00024414이고 투과율·가중 깊이 차이는 0.
- 기존 형태 검사: 상층 65,536개, 경계 20,800개 표본, 연속 운해·GPU 자원 재사용 검사 통과.
- 환경 검사: 날씨 전환 중단·재전환 및 즉시 전환 통과.
- HDRP 장면: EV+1 비율 0.5, 전경 팔레트 영향 0, 태양 동기화·공유 하늘 에셋 불변 통과.
- 실제 Play 입력: F8 열기, Esc 닫기, 비행 입력 중단·복구, 해상도 및 최적화 10회 전환, 안정 상태 버퍼·셀 캐시 재생성 없음.
- Unity MCP 최종 컴파일 및 Play Console 오류·경고 없음. 최종 기본 OFF 설정에서도 Play 검사를 다시 통과했다.
- 고정 home 구간 OFF/ON 1280×720 캡처와 544×456 및 FHD 설정창을 확인했다. 정지 합성 캡처에는 HDRP 이력 차이가 있을 수 있으며 엄격한 출력 비교는 별도 GPU 버퍼 검사 결과를 사용한다.

Play에서 **F8** 또는 우측 하단 **Cloud settings**로 연다. `Skip empty cloud regions`와 `Stop negligible shadow work`는 기본 OFF이며 같은 시점에서 하나씩 비교한다. `Restore session defaults`로 시작 설정을 복원하고 F8/Esc로 닫는다. 변경은 해당 Play 실행에만 적용된다. 기존 셀 캐시·지원 범위 검사·압축 버퍼의 기본 ON은 유지했다.

## 남은 목표와 후속 판단

**GTX 1660 FHD 60 FPS 달성은 확인하지 못했다.** RTX 4080의 일부 시점에서 레이마칭만으로 16.67ms를 크게 초과한다. 이번 개선을 목표 장비 FPS로 환산하지 않는다. 실제 GTX 1660 Player 측정과 급회전·전경·장시간 검사도 남아 있다.

추가로 큰 비용을 줄이려면 저해상도 깊이 인식 재구성 또는 픽셀 간 조명 조회 공유처럼 계산 구조를 바꾸는 후보가 필요하다. 경계 품질·얇은 띠·조명 오차를 별도 판단해야 하므로 자동으로 개발 범위를 확대하지 않았다. 시간 재투영과 유체 반응도 이번 구현에 포함하지 않았다.
