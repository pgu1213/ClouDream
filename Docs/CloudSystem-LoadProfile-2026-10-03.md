# 현재 구름 시스템 처리 부하 보고서

2026-10-03 KST. RTX 4080 / i7-13700K / Unity 6000.6.2f1 / HDRP / Direct3D12 / Editor Play.

현재 가장 큰 병목은 **GPU의 구름 광선 추적(Raymarch)**이다. 일반적으로 관측된 구름 GPU 시간은 프레임당 약 32~34ms이며, 별도 실행에서는 53.05ms까지 증가했다. 구름 내부에서 밀도장·표면 법선·조명용 차폐를 반복 평가하는 비용이 지배적이다. 깊이 복사와 최종 화면 합성은 합쳐 약 0.05ms다. CPU의 큰 프레임 시간은 대부분 GPU 완료 대기이며, 구름의 CPU 명령 준비는 표본 구간에서 약 0.1ms 수준이었다.

기능을 제외한 진단에서 법선과 조명 계산을 줄일 여지는 확인했다. 그러나 이 진단은 화면을 바꾸므로 그대로 채택할 최적화가 아니다. 현재 결과만으로 화질을 유지하며 RTX 4080의 FHD 240FPS를 달성할 수 있다고 판단할 수 없다.

## 성능 목표와 의미

사용자 요청에 따라 GTX 1660 실측에 종속된 평가 대신 **RTX 4080 / FHD / 전체 프레임 240FPS = 4.17ms**를 임시 개발 목표로 삼는다.

Tom’s Hardware의 동일한 2022–2024 래스터 게임 시험에서 RTX 4080/GTX 1660의 비율은 1080p Ultra에서 147/42.6 ≈ 3.45배, 1440p Ultra에서 130.4/30.3 ≈ 4.30배였다. 이전 60FPS 목표에 적용하면 약 207~258FPS 범위다. FHD 직접 비교는 약 207FPS이며, 240FPS는 이 범위 안에서 여유를 요구하는 **우리 프로젝트의 잠정 목표**다. [원 측정 자료](https://www.tomshardware.com/reviews/gpu-hierarchy,4388-2.html)

이 비율은 해당 게임 묶음의 결과이며 이 Compute 셰이더의 GPU 간 배율을 보장하지 않는다. 본 구름은 DXR 하드웨어 레이 트레이싱이나 DLSS를 사용하는 경로가 아니므로 그 성능 배율을 적용하지 않았다. 향후 실제 게임 장면과 Player 빌드에서 목표의 적절성을 다시 확인해야 한다.

구름 단독 32~34ms는 전체 목표 예산 4.17ms의 약 8배다. 다른 렌더링과 게임 로직의 시간을 남기기 위해 구름에 **약 2ms**를 배정한다면 현재 대비 약 94% 감소가 필요하다. 2ms는 측정 결과나 업계 보편 기준이 아니라 작업 우선순위를 정하기 위한 제안 예산이다. 소폭의 분기 최적화만 반복해서 해결될 크기의 격차는 아니다.

## 측정 범위와 통제

- 장면: `Assets/LostSkiesClouds/Scenes/LostSkiesCloudSea.unity`, Concept V2.
- 출력 1920×1080, 구름 75% 해상도인 1440×816. 8픽셀 dispatch 단위 정렬 때문에 높이는 810이 아닌 816이다.
- 셀 캐시·지원 범위 검사·압축 버퍼·깊이 업샘플링 ON. 시간 재투영·거리별 밀도/조명 품질·빈 공간 교차 구간·공간 조명 캐시·팔레트 전용 경로·그림자 조기 종료 OFF. **기존 최적화 옵션을 모두 활성화한 최종 품질 프리셋의 성능이 아니다.**
- 정오 12시, 바람 0, 게임 시간 정지. VSync 및 FPS 제한 해제. 입력과 카메라는 기존 벤치마크가 제어한다.
- CloudRoute-v1의 상층 회전·관통·운해 경로를 각각 180프레임씩 실행했다. 조건마다 전체 경로 540프레임 워밍업 후 540프레임 측정하며, 준비·GPU 기록 배출 프레임은 측정에서 제외한다.
- 전체 비교, 편차 재확인, 법선/조명 재확인의 세 묶음으로 정순/역순 반복한다. 기능을 제외하는 셰이더는 진단용 임시 복사본이다. 원본 실행 셰이더와 직렬화된 품질 설정은 변경하지 않는다.
- CPU는 각 실행이 끝나기 40프레임 전을 끝으로 최근 60개 프로파일러 프레임을 내보냈다. 운해 경로 후반의 표본이므로 경로 전체 평균 CPU 비용으로 일반화하지 않는다.
- GPU 호출 횟수 검사는 별도 320×184, 18개 자세에서 수행했다. 장면 깊이가 없는 독립 검증 환경이므로 FHD 실행 횟수로 환산하지 않는다. 카운터가 추가된 셰이더의 실행 시간도 성능 지표로 쓰지 않는다.

Editor와 프로파일러 자체의 비용이 포함되어 있다. 실제 게임 비용은 Player 빌드에서 확인해야 한다. Unity도 Editor와 대상 기기 프로파일링의 차이를 명시한다. [Play 모드 측정](https://docs.unity3d.com/6000.0/Documentation/Manual/profiling-play-mode.html), [대상 기기 측정](https://docs.unity3d.com/6000.0/Documentation/Manual/profiling-target-device.html)

## GPU 처리 구조와 병목

`Cloud.Total`은 깊이 복사, 구름 추적, 합성을 둘러싼 GPU 범위다. `Cloud.Raymarch`는 그 내부에 포함된다. 따라서 “셰이더 33ms + 구름 렌더링 33ms = 66ms”로 합산하면 안 된다. CPU의 명령 준비 시간 역시 GPU와 병렬로 진행될 수 있다.

마지막 재확인 묶음의 기준선 2회, 총 1,080프레임 평균은 아래와 같다. 기준선 평균 FPS는 총 프레임/총 시간으로 계산한 **28.52FPS**, 프레임 간격 평균 35.06ms, p95 50.35ms, 최저 16.00FPS였다. 두 실행의 1% low는 16.85/16.65FPS다.

| 단계 | GPU 평균 ms/프레임 | 포함 관계와 의미 |
|---|---:|---|
| 전체 GPU 프레임 | 35.020 | 이 묶음은 FrameTiming GPU sanity 검사 통과 |
| 구름 전체 `Cloud.Total` | 33.391 | 전체 GPU 시간의 약 95.3% |
| 구름 추적 `Cloud.Raymarch` | 33.337 | 구름 전체의 약 99.84%; 밀도·법선·조명·적분 포함 |
| 장면 깊이 복사 `Cloud.DepthCopy` | 0.0075 | 구름 전체에 포함 |
| 확대 및 합성 `Cloud.Composite` | 0.0455 | 구름 전체에 포함 |
| 전체 GPU와 구름 평균의 차이 | 약 1.63 | 나머지 HDRP·UI 등의 합계에 대한 근사 잔여값 |

마지막 행은 별도 패스 타이머가 아니다. GPU 표본 스트림은 지연되므로 개별 카메라 자세와 직접 대응시키지 않았고, 경로 전체 평균만 비교했다. GPU RawFrameData의 별도 운해 후반 표본도 35.91/33.79ms로 수십 ms의 전체 GPU 시간을 확인했다.

현재 값에서는 화면 합성만 개선하거나 C# 호출을 줄이는 작업으로 수십 ms를 제거하기 어렵다. GPU 사용률은 두 기준 실행 모두 100%였고 평균 클록은 약 2740MHz였다. 사용률은 NVML 어댑터 전체 값이다.

깊이 복사는 주 광선이 장면 지오메트리 뒤까지 진행하지 않게 하는 보조 단계다. 합성은 구름 색과 투과율을 깊이 정보에 맞춰 확대하고 HDRP 화면에 적용한다. 두 단계의 비용은 현재 해상도에서 작다. `Raymarch` 마커는 GPU dispatch 범위이며 CPU의 `Compute.Dispatch` 호출 시간과 구분해야 한다.

같은 최종 묶음에서 기능을 제외한 결과는 다음과 같다. GPU 반복 편차는 `(두 평균의 차이)/(두 평균의 평균)`이며 통계적 신뢰구간은 아니다.

| 진단 조건 | 정순/역순 구름 GPU ms | 평균 GPU ms | 합산 FPS | 기준 대비 GPU 감소 | 반복 편차 |
|---|---:|---:|---:|---:|---:|
| 현재 기준선 | 33.91 / 32.87 | 33.39 | 28.52 | — | 3.11% |
| 표면 법선을 상수로 대체 | 22.47 / 22.06 | 22.26 | 41.76 | 11.13ms, 33.3% | 1.84% |
| 하늘 차폐 조회 제외 | 23.87 / 23.63 | 23.75 | 39.36 | 9.64ms, 28.9% | 1.01% |
| 모든 입사광을 상수로 대체 | 11.32 / 10.83 | 11.07 | 78.54 | 22.32ms, 66.8% | 4.36% |

법선 제외는 첫 묶음에서도 22.30/22.00ms, 상수 조명은 10.83/10.82ms로 큰 감소가 재현됐다. **법선과 조명 전체를 우선 조사할 근거는 강하다.** 상수 조명은 사용되지 않는 법선·차폐·색 계산까지 컴파일러가 제거할 수 있으므로, 법선 제외와 겹치는 진단이다. 남은 약 11ms는 밀도 추적·경계 탐색·적분·루프 등을 포함하며 순수 Density 함수만의 시간은 아니다.

태양 차폐 제외는 별도 두 묶음에서 22.73/19.39ms와 18.92/19.37ms였다. 감소 방향은 일관되지만 묶음의 기준선 편차가 커 **태양 그림자의 독립 비용을 특정 ms로 확정하지 않는다.** 하늘 차폐도 최종 묶음에서는 감소했으나 다른 묶음에서 21.29~35.20ms까지 달라져 28.9%를 일반적인 개선율로 사용하지 않는다.

구름 패스 전체를 끈 경우 첫 묶음 251.53/257.33FPS, 두 번째 묶음 290.05/290.34FPS였다. 두 번째의 합산은 약 290.20FPS, 프레임 간격 약 3.45ms다. `Cloud.Total`이 기록되지 않는 상태는 GPU 비용 0ms 실측이 아닌 **패스 미실행/마커 없음**으로 보존했다. 이 조건과 현재 구름을 사용하는 조건의 큰 차이는 병목을 구름으로 좁히는 근거다.

| 실제 밀도가 있는 내부 적분 | 29,808,288 | 주 루프의 6.28%; 나머지가 모두 같은 비용인 것은 아님 |

전체 `Density` 호출은 553,213,133회, 광선당 평균 521.98회다. MacroField 조회는 이 합계에 포함하지 않았다. 1024회 주 루프 상한에 도달한 광선은 이 표본에서 0개였다. 상한까지 불필요하게 반복하는 현상은 관측하지 못했다. 상한을 현재 필요한 반복 수보다 낮추면 표본을 줄일 수 있지만 구름이 잘리는 등 결과가 달라질 수 있다.

각 구간은 353,280개 광선이며, 광선당 주 루프 평균은 상층 회전 525.11회, 관통 372.49회, 운해 445.11회였다. 운해는 내부 적분과 입사광 평가가 더 많았다. 따라서 가장 많은 루프를 돈 구간이 반드시 가장 느린 구간인 것은 아니다.

구체적인 고비용 경로는 다음과 같다.

1. **주 밀도장 평가:** ConceptDensity는 운해·상층·띠구름을 합성한다. 지원 범위 밖에서는 일찍 반환하지만, 유효 영역에서는 형태 필드와 3D 노이즈를 평가한다. 상층의 상세 형태는 최대 14개, 단순 형태는 5개의 타원체 필드를 조합한다. 셀 캐시는 중심·크기 같은 불변값을 재사용하며 위치별 필드 평가 전체를 없애지는 않는다.
2. **표면 법선:** 구름에 진입할 때 상세 밀도를 6번, 큰 형태 필드를 6번 평가하고 법선 간격을 위한 형태 검색도 수행한다. 모든 내부 적분 표본마다 계산하지는 않지만, 각각이 비싼 형태 계산을 다시 포함한다.
3. **조명 차폐:** 입사광 한 번당 태양 방향 7개와 위쪽 3개의 밀도 표본을 조회한다. 현재 60m 간격의 광선 내 조명 보간이 있어도 총 약 6,897만 번의 조명용 밀도 조회가 남았다.
4. **내부 적분 간격:** 구름 내부 표본 간격은 기본적으로 5~18m 범위다. 투과율이 0.008 이하가 되거나 종료 거리에 도달할 때까지 진행한다. 안정적인 곡면과 명암을 얻기 위해 사용하는 반복의 비용이다.

3D 노이즈를 매 표본마다 새로 생성하는 구조는 아니다. 사전에 생성한 텍스처를 조회한다. 밀도 호출 개수를 시간 비율로 바꾸는 것도 잘못이다. 빈 위치에서 일찍 반환하는 주 조회와, 유효 표면의 법선·차폐 조회는 서로 다른 일을 한다.

| `RecordRenderGraph` | 0.362 | 렌더 그래프 구성, HDRP 범위에 포함 |
| 구름 CustomPass 실행 | 0.117 | 구름 데이터/명령 준비; GPU의 33.39ms와 구분 |
| 시간대 컨트롤러 Update | 0.031 | 고정 시간에서도 조명 상태 적용 |
| 벤치마크 LateUpdate | 0.034 | 경로 진행 및 표본 수집 |
| 벤치마크 OnGUI | 0.161 | 계측 UI 비용, 프레임당 합산 |
| 프로파일러 메모리 카운터 | 0.258 | 측정 도구 자체 비용 |
| EditorLoop | 1.468 | 에디터 작업, Player 게임 로직 비용과 구분 |

메인 스레드 시간이나 Render Thread의 `RenderLoop` 자체 시간이 크다고 해서 동일한 길이의 C# 연산이 있다는 뜻은 아니다. 후자는 표시되지 않은 대기와 네이티브 작업도 포함할 수 있다. 부모/자식 inclusive 시간은 중복되므로 더하지 않는다. 구름을 끈 첫 비교의 CPU 표본에서 HDRP는 약 1.89ms, EditorLoop는 약 1.48ms였고 큰 GPU 대기는 사라졌다.

기준선 두 실행의 평균 프로세스 CPU 사용률은 각각 약 1.66%와 1.58%다. 이는 24개 논리 코어로 정규화한 프로세스 지표이므로 낮은 수치만으로 메인 스레드 여유를 판정하지 않는다. 직접적인 판정 근거는 위의 CPU 마커와 GPU 대기다.

최종 기준선의 GC 할당 카운터는 평균 약 20.4KiB/프레임, 1,080프레임 중 GC 횟수 합계 2였다. Editor·벤치마크·GUI를 포함한 값이며 구름 런타임 코드의 순수 할당량으로 귀속할 수 없다. 하드웨어 조회는 약 1초 간격이고 호출당 평균 0.63ms, 최대 2.09ms였다. 이는 매 프레임 0.63ms라는 뜻이 아니다.

게임 시간을 정지했으므로 정상적인 FixedUpdate 물리, 실제 플레이어 이동, 전투, AI, 동적 날씨 전환의 최악 부하는 이번 결과에 들어 있지 않다. 이 보고서로 향후 완성 게임의 CPU 예산까지 보장하지 않는다.

구름 리소스의 확인 가능한 상주 규모는 다음과 같다.

| 리소스 | 규모 | 갱신 특성 |
|---|---:|---|
| 색/깊이·투과율·장면 깊이 RT 합계 | 17.93MiB | 고정 해상도 실행에서 할당 횟수 1 유지 |
| 3D 노이즈 텍스처 6개 | 약 43.72MiB | mip 포함, 생성 시 또는 해당 경로 최초 사용 시 준비 |
| 형태 셀 캐시 | 0.50MiB | 32×32셀 × 셀당 float4 32개; 셀 기준 또는 설정 변경 때 재구축 |
| 확인된 구름 리소스 소계 | 약 62.15MiB | 드라이버 정렬·기타 관리 비용·다른 카메라 제외 |

노이즈 값은 Unity의 런타임 리소스 크기 조회이며 객체 관리 비용을 일부 포함한다. 다른 GPU 버퍼 및 HDRP 카메라 버퍼 전체를 합친 VRAM 값과 같지 않다. 예를 들어 HDRP의 색 피라미드와 AO 이력은 별도 카메라 리소스다. 비활성 시간 재투영·공간 조명 캐시는 이 실행의 활성 RT 예산에 포함되지 않았다.

Editor 프로세스 RAM은 약 4GiB, Unity 할당은 약 3.4GiB, 어댑터 전체 VRAM은 약 5.8~6.1GiB 수준이었다. 어댑터 값에는 다른 앱도 들어간다. 측정 중에는 구름 GPU 시간이 압도적이며, 현재 자료에서 용량 부족이 주 병목이라는 증거는 없다. NVML의 memory-busy 비율은 대역폭 포화율이 아니므로 그 값만으로 메모리 병목을 배제하지 않는다. [리소스 원본](D:/Dev/ClouDream/Benchmarks/SystemLoad-Memory.json)

## 진단 결과의 한계와 다음 판단

이번 조명 제외 셰이더의 시간 차이는 **그 코드를 생략했을 때 전체 dispatch가 변한 양**이다. GPU 함수별 독립 타이머가 아니다. 컴파일러의 코드 제거, 레지스터 사용량, 분기와 실행 효율 변화도 포함될 수 있으므로 법선·태양·하늘 차폐의 절감량을 합산하지 않는다. Nsight 수준의 명령별 시간, 레지스터 spill, wave occupancy, 캐시 적중률은 측정하지 않았다.

반복이 흔들린 항목은 단일 절감률을 확정하지 않는다. 계수 결과는 어떤 작업이 많은지 설명하지만, 하드웨어 비용을 직접 배분하지 않는다. 과거 빈 공간 조회 감소가 FPS 향상으로 이어지지 않은 결과도 같은 이유로 해석해야 한다.

우선순위는 **법선·조명용 형태 재평가를 줄이는 설계 검토**, 다음으로 **프레임당 추적 픽셀 수와 내부 표본 수를 줄이면서 움직임 품질을 유지하는 검증**이다. 법선을 상수로 바꾸거나 조명을 없애는 진단 결과 자체를 제품에 채택하지 않았다. 실제 도입은 기능별로 따로 비교하고, 구름 모양·빛의 방향·시간 전환·이동 중 잔상을 확인해야 한다.

현재 구조에도 개선 여지는 있지만, 240FPS 목표에는 수십 퍼센트의 개선을 넘어 반복 계산의 규모를 크게 줄일 필요가 있다. 따라서 “현재 선택 옵션을 더 켜면 게임 최적화가 완성된다”는 결론은 아직 근거가 없다.

## 반복 편차와 데이터 품질

총 28회 × 540프레임 = **15,120개 측정 프레임**을 확보했다. 워밍업은 별도다. 최종 묶음의 여덟 조건은 카메라 자세 배열·해상도·시각·정지 게임 시간·형태 프로필이 같고, 각 실행의 GPU 표본 540개와 FrameTiming sanity 통과를 확인했다. 기준 셰이더 해시는 동일하다.

| 묶음 | 기준선 GPU 정순/역순 ms | 주요 관찰 |
|---|---:|---|
| 첫 전체 비교 `154944` | 32.93 / 32.91 | GPU 기준선 안정, 태양·하늘 제외는 편차 큼 |
| 편차 재확인 `160306` | 53.05 / 32.21 | 기준선 자체가 약 48.9% 변동; 평균 42.63ms를 대표값으로 쓰지 않음 |
| 최종 재확인 `161141` | 33.91 / 32.87 | 기준선 편차 3.11%; 위 단계별 표의 기준 |

53.05ms 실행의 평균 FPS는 18.29였다. 이를 지우거나 측정 실패로 단정하지 않았다. 카메라 경로·옵션·시각이 같고 GPU 클록도 약 2745MHz였지만 원인을 확정하지 못했다. 셰이더/드라이버의 실행 상태, 다른 GPU 작업, Editor 영향 등을 추가로 분리하지 않았으므로 특정 원인으로 설명하지 않는다. 대표 수치는 최종 통제 반복을 사용하면서 전체 범위를 함께 공개했다. 최종 묶음의 재현성은 세션을 바꿔도 항상 같은 비용이라는 보증은 아니다.

첫 묶음 후반의 한 프레임은 약 978ms로 튀었다. 측정 중 MCP 동적 코드 조회가 개입한 실행이므로 최저 FPS/전체 FPS 비교에 부적합하다. 해당 원시 기록은 보존하고 이후 두 묶음에서는 타이밍 수집 중 Unity 코드 실행을 하지 않았다. Shader 초기 컴파일·노이즈 초기 생성 비용은 워밍업 전후에서 처리되므로 이 결과는 초기 로딩 지연 평가가 아니다.

첫 묶음 앞부분의 FrameTiming GPU는 약 0.03ms로 Cloud.Total 약 33ms와 모순됐으며, 기존 sanity 검사도 실패했다. 그 값을 전체 GPU 시간으로 쓰지 않았다. 최종 묶음은 모든 조건에서 sanity를 통과했고 Profiler RawFrameData의 별도 GPU 프레임 시간과도 규모가 일치했다. 구름 패스를 끈 실행은 기준 Cloud 마커가 없어 같은 sanity 검증이 성립하지 않으므로, 보고한 OFF FPS는 실제 프레임 간격을 사용한다. Draw-call 카운터도 0 또는 불완전한 표본을 보여 병목 판단에서 제외했다.
